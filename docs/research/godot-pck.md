## Findings that shape the manifest/SDK design

1. **A `.pck` is a resource pack, not a running sub-project.** `godot
   --headless --export-pack "<preset>" out.pck` packs the *files* of a
   Godot project (scenes, scripts, assets) preserving their `res://` paths
   relative to that project's root. **Consequence:** an activity's own
   `project.godot` is a local-dev/preview convenience only (`godot --path
   activities/_template` to iterate without the shell) — verified directly
   (not assumed): exporting `/activities/_template` with `--export-pack`
   and an `exclude_filter` of `project.godot` produces a `.pck` that does
   *not* contain the source `project.godot` file. **One caveat found by
   testing, not by reading docs:** Godot's exporter unconditionally writes
   a compiled `res://project.binary` into every resource pack regardless
   of `exclude_filter` — this is the engine's own internal compiled
   settings blob, generated by the export pipeline itself, not something
   `exclude_filter` can suppress. It's small (part of a 34.9K test export)
   and not something this research established the runtime effect of: it's
   still unconfirmed here whether `ProjectSettings.load_resource_pack()`
   merges `project.binary`'s contents into the host shell's already-running
   `ProjectSettings` singleton, and if so, whether anything in it (e.g. the
   activity's own `renderer/*` or `window/*` keys) could clobber the
   shell's live settings. **T1.4 must confirm this directly against the
   real engine before shipping real PCK loading** — flagged here rather
   than asserted either way.

2. **`res://` paths in a loaded PCK are whatever the source project's paths
   were.** For the shell to find an activity's entry scene and manifest
   after `load_resource_pack`, the SDK must fix a path *convention*
   (`res://manifest.cfg`, `res://activity.tscn` at each activity project's
   root) rather than discover them dynamically — Godot gives no
   PCK-level "list contents" API suited to this at runtime in a way
   that's simpler than just agreeing on fixed names.

3. **`class_name` global registration does not span a dynamically loaded
   PCK.** `shell/README.md` already documents that global class
   registration (`Shell`, `ActivityBase`, ...) is built by an *editor-mode
   project scan* of the shell's own project, cached in
   `.godot/global_script_class_cache.cfg` — a per-project, build-time
   artifact. A PCK loaded at runtime via `load_resource_pack` was never
   scanned into the *host* shell's class cache, so a custom
   `class_name ActivityManifest` resource *defined inside an activity's
   PCK* would not reliably resolve when the shell tries to load it.
   **Consequence:** the manifest format must use only Godot's built-in,
   always-available types — `ConfigFile`, not a custom `Resource` subclass
   with a `class_name`. `ActivityBase` itself is fine as a `class_name`
   because it lives in the *shell's own* project (`shell/scripts/`), not
   inside a PCK; activities extend it by `extends "res://addons/
   covelight_sdk/activity_base.gd"` (path-based `extends`, not
   `extends ActivityBase`) so their scripts don't depend on the global
   class name resolving inside their own separately-loaded project either
   — though for an activity's *own* editor session (previewing it
   standalone), `class_name` works fine since that project scans itself.
   Practically: the SDK script the activity extends should be reachable
   at the same relative path in both contexts, which the symlinked
   `addons/covelight_sdk/` layout (below) guarantees.

4. **No supported way for one Godot project to depend on another's source
   short of a shared file on disk.** Each activity needs its own
   `project.godot` (to export its own PCK independently), but must share
   exactly one copy of the SDK GDScript source with the shell and every
   other activity (ADR 0002's "ecosystem-wide events" point — an SDK
   change must not require hand-syncing N copies). The standard pattern in
   multi-project Godot monorepos is a relative symlink:
   `activities/_template/addons/covelight_sdk -> ../../../shell/sdk`.
   Godot's exporter reads through symlinks like any other file at the OS
   level, so packing resolves real bytes normally. **Accepted cost:** git
   symlinks work natively on macOS/Linux (this project's dev environments
   per ARCHITECTURE §7); Windows contributors need
   `git config core.symlinks true` plus Developer Mode or an elevated
   prompt to materialize them. Documented as a known rough edge in
   `docs/guides/building-activities.md`, not hidden.

5. **`--export-pack` is the CLI path CI/maintainers use to produce the
   `<id>.pck` that `tools/sign` then signs** (`docs/design/signing.md`
   treats the `.pck` as an opaque byte string it never has to parse) — this
   confirms the sign/export split assumed by that doc: export first
   (Godot), sign second (`covelight-crypto`), always as a pair.
