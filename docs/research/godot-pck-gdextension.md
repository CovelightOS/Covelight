# Godot 4 runtime PCK loading + GDExtension on Android

**Researched:** 2026-07-14 · **Sources:** NotebookLM query against the "Covelight" notebook (61 sources: Godot 4 class-ref docs for `ProjectSettings`/`PCKPacker`, godot-proposals issue #13231 "Add ability to load PCK files from memory", a reddit.com/r/godot thread on signing patches with RSA/SHA-256 and TOCTOU, the CAVS Godot Asset Store listing + forum post (GDScript PCK content-delivery toolkit with optional signature verification), godot-rust/gdext cross-compilation docs (Android NDK targets), F-Droid inclusion-policy pages, and this repo's own `docs/design/signing.md`/`CLAUDE.md`/`docs/plan/02-phase1-shell.md`, which the notebook had already ingested). Cross-checked the `godot`/`gdext` crate's Godot-version compatibility claim via a live web search (godot-rust book, 2026-07-14) since NotebookLM's sources didn't pin an exact crates.io version.
**Confidence:** high on the core question (path-only loading, no pre-mount hook, TOCTOU risk) — corroborated by an official Godot engine proposal issue, a primary community thread, and this project's own prior analysis, all converging independently. Medium on Android-specific GDExtension packaging details (NDK version, F-Droid source-build requirement) — plausible and internally consistent, but not independently re-verified against current godotengine.org docs beyond the one compatibility check above. Low/unconfirmed on the exact behavior of `project.binary` inside a resource pack at merge time (carried over from `docs/research/godot-pck.md`, not re-resolved here).
**Affects:** T1.4 (blocks — this is the research gate the task required before implementation). Also relevant to T2.1 (Android kiosk wrapper, Phase 2) for the GDExtension/NDK packaging details below, which T1.4 itself doesn't need yet.

## The core question: can we verify before `load_resource_pack`?

**Yes — this is what the research supports doing, and it's what `docs/design/signing.md` already assumes. No contradiction found.**

- `ProjectSettings.load_resource_pack(path, replace_files, offset)` accepts **only a physical file path**. There is no in-memory buffer variant, no pre-mount callback/hook, and no way to hand it an already-open, already-verified file handle — it opens its own handle internally. This is confirmed by Godot's own class reference and, independently, by an **open (later closed-as-archived) engine proposal, godot-proposals #13231, "Add ability to load PCK files from memory,"** whose entire premise is that this capability doesn't exist today and would need new engine code (`load_resource_pack_from_buffer`, an `add_pack(Ref<FileAccess>, ...)` signature change) to add it.
- Because there's no pre-mount hook *inside* Godot, the verification has to happen **entirely outside and before** the `load_resource_pack` call — exactly the shape `docs/design/signing.md` already specifies (steps 1–5 read and verify the sidecar + hash the `.pck` from disk via ordinary file I/O; step 6 is "only on success, proceed to load `<id>.pck` through the normal Godot resource-pack path"). Treating the `.pck` as an opaque byte blob, verifying it with normal file I/O, and only then handing the same path to `load_resource_pack` is confirmed as the standard approach — both by the CAVS toolkit (an existing open-source Godot 4 addon doing exactly this: reconstruct → verify → `load_resource_pack()`) and by a Reddit thread of Godot developers discussing the identical RSA/SHA-256-sign-then-verify-then-load pipeline for patch files.
- **Conclusion: proceed.** The plan's core assumption holds. `/tools/covelight-crypto`'s `verify_file()` (streaming SHA-512, constant memory) run against the `.pck` path, followed by `ProjectSettings.load_resource_pack(path)` only on `Ok`, is exactly the shape the engine supports and the only shape it supports.

## Residual risk found, not previously documented: TOCTOU

Because verification and loading are two separate file-open operations rather than one atomic one, there is a **Time-of-Check-to-Time-of-Use window**: between our GDExtension verifying the file and Godot's own internal `load_resource_pack` open-and-read, another process with write access to that exact path could swap the file's contents.

- Godot gives no way to pass a verified, already-open file handle into `load_resource_pack` — it always opens its own.
- Standard file locks (`flock` and equivalents) are **advisory, not mandatory** on Linux and Android: a second process can simply ignore an existing lock and overwrite the file while it's held open by another process. (Windows can obtain a genuinely exclusive write handle via a WinAPI flag — not relevant to this project's Linux/Android targets.)
- No full mitigation exists at the Godot API level today; the only real fixes are either engine-level (the still-open proposal for in-memory loading) or OS-level (mandatory locking, SELinux enforcement, or a filesystem/process boundary that makes the attack impossible rather than merely inconvenient).

**Why this doesn't block T1.4, and why it doesn't contradict the approved design:** `docs/design/signing.md`'s own stated threat model already excludes "someone with root/fastboot access" and "a fully compromised device" — a TOCTOU attacker needs *write access to the exact on-device path the shell reads the PCK from*, at the exact moment between verify and load. On both tiers, that path is not attacker-reachable without something already outside signing's stated threat model:

- **Tier 1:** the content directory is the Covelight app's own private storage. No other unprivileged Android app can write there; something that could would already need root or a platform compromise — out of scope per the doc's own "Not the adversary" section.
- **Tier 2:** privilege separation (CLAUDE.md #14) means the `kid` process that reads and loads content cannot write to the content store at all; only `sync` can. A TOCTOU write would require a compromised `covelight-syncd` — a more relevant threat than Tier 1's, but still a different (and larger) problem than "this PCK's signature wasn't checked," and one `covelight-syncd`'s own pre-auth design (CLAUDE.md #12) is what's meant to defend against.

**What T1.4 does anyway, as cheap defense-in-depth, without claiming it closes the window:** verify immediately followed by load, with no unrelated I/O or scheduling gap between them, minimizing (not eliminating) the window. This is stated as a mitigation of degree, not a fix — consistent with this project's existing honesty about limits it can't structurally close (ARCHITECTURE §8, `docs/design/signing.md`'s own "Non-goals" section, which is getting a short addition to name this one explicitly).

## Other findings, informational (don't change T1.4's implementation)

- **`class_name` in a dynamically loaded PCK doesn't register into the host's global class database**, because that database is built once at startup. This was already independently discovered and designed around in T1.3 (`docs/research/godot-pck.md` finding 3; the activity manifest is a plain `ConfigFile`, never a custom `class_name` `Resource`). Corroborated again here from an independent angle — no action needed, just cross-referenced.
- **No API to unmount/unload a loaded resource pack.** Once `load_resource_pack` succeeds, that content stays mounted until process restart. Not a T1.4 concern (verifying and loading one activity at a time doesn't need unmounting), but worth flagging for whoever eventually handles "the shell has been open a long time and loaded many different activities" — a future task, not this one.
- **GDExtension on Android** (relevant to T2.1, not T1.4, which targets desktop/CI Linux like the rest of `/shell` so far): cross-compiling the Rust `cdylib` needs `aarch64-linux-android` (primary) and `armv7-linux-androideabi` (legacy) targets, Android NDK r27c (LTS, the version Godot 4.5+ docs recommend), and can't be done from an arm64 Linux *host* (Google ships no NDK toolchain for that host) — x86_64 Linux or native macOS (this project's actual dev machines, per ARCHITECTURE §7) both work. F-Droid's source-only inclusion policy means the GDExtension `.so` can never be shipped as a prebuilt binary blob in the F-Droid build — it has to compile from source via Cargo + NDK on F-Droid's own infrastructure, same discipline `/tools/sign` already follows (plain `cargo build`, no vendored binaries). None of this blocks T1.4; noting it now so T2.1 doesn't have to rediscover it.
- **`godot` (gdext) crate / Godot 4.7 compatibility**, checked directly (web search, 2026-07-14, not from the notebook): GDExtension's own forward-compatibility guarantee means an extension built against API level 4.2+ loads fine on a newer runtime like 4.7, provided runtime version ≥ API version. The exact crates.io patch version wasn't pinned by any source consulted — resolved at implementation time via `cargo add godot`, not hand-typed, so the actual dependency line reflects a real, currently-published version rather than a guessed one.

- Whether `ProjectSettings.load_resource_pack()`'s internal merge of a pack's `project.binary` (see `docs/research/godot-pck.md`) could ever matter for a *content* PCK signed and loaded this way — carried over as still-open from T1.3's research, unaffected by anything found here since activity PCKs and the verification step are orthogonal to that question.
- Real-world TOCTOU exploitability on Tier 1 hasn't been tested against an actual Device-Owner-provisioned Android install (only reasoned about from Android's app-sandboxing model) — a `[human]`-flagged verification task for whenever Tier 1 device testing (Phase 3) is underway, not a blocker now.
